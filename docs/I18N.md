# Internationalization

My Morning News ships its interface in 12 languages plus two pseudo-locales for testing. This document covers the locales, how the catalogs are organized, how to add a key or a locale, what the verifiers check, and how the right-to-left and expansion smoke tests work.

> **Translation status.** English is the source. The other 11 catalogs (dashboard and mobile) were machine-translated and have not yet been reviewed by native speakers. Treat them as a complete first draft: they are grammatical, use consistent terminology, and keep every placeholder, but a native reviewer should check tone, terminology, and fit before a public launch. Report or fix wording in the catalog files directly; the verifiers keep every edit valid.

The registry lives in `dashboard/src/i18n/localeRegistry.js` and is mirrored in `mobile/src/i18n/locales.js`. Locale resolution is: an explicit choice (the language selector on the login page, the top bar, and settings, stored under `mymorningnews.locale`), then the browser or device language, then English. Regional tags and aliases are normalized (`en-US` to `en`, `zh-Hans` to `zh`). The active locale sets `lang` and `dir` on the document, formats numbers and dates through `Intl` with that locale, and is sent to the server as `Accept-Language`.

Product names stay in English in every locale: My Morning News, Claude, Anthropic, OpenAI, Gemini, MCP, SearXNG, Ollama, Kokoro, Mailgun, and the other vendor names. So do code, identifiers, environment variables, cron syntax, URLs, HTTP methods, and route paths.

## How the catalogs are organized

### Dashboard

- `dashboard/src/i18n/locales/<code>.json`: one nested JSON file per locale. Top-level keys are namespaces (`common`, `nav`, `topics`, `insights`, and so on); messages are ICU MessageFormat strings. Every catalog has exactly the keys of `en.json`, about 2,900 of them.
- `dashboard/src/i18n/resources.js`: English is bundled. The other catalogs are found with `import.meta.glob`, so Vite builds each into its own chunk that loads the first time its locale is selected. The pseudo-locales are generated from English at load time (`pseudo.js`).
- `dashboard/src/i18n/index.js`: i18next with `i18next-icu`. English is the fallback language, so a key that is somehow missing at run time shows English rather than a raw key.
- Enum display labels (statuses, tiers, providers, stages) are keyed by their stable server codes under `enums.*`.

### Mobile

- `mobile/src/i18n/catalog/<code>.js`: one module per locale exporting the app's own strings, which the runtime mounts under the `mobile.*` key prefix. Same ICU syntax as the dashboard. Every catalog has exactly the keys of `en.js`, about 1,100 of them.
- `mobile/src/i18n/catalog/index.js` registers the catalogs and builds the pseudo-locales from English. When the dashboard catalog moves to `dashboard/src/shared/` (see `mobile/sharing.config.js`), its translations join the same i18next instance beside `mobile`.

### Server

Email chrome (subject lines, headings, button and footer labels) and the public feedback and unsubscribe pages are rendered in English today. The strings are inline in `src/MyMorningNews.Core/Email/EmailService.cs`, `EmailActions.cs`, and `PublicPages.cs`. Plan section 25.7 calls for a server-side catalog keyed by the recipient's preferred locale. That needs:

1. A string catalog in Core (for example `Localization/ServerStrings.cs` with one resource file per locale) with a lookup that takes a locale and a key, falls back to English, and formats placeholders.
2. The recipient's locale threaded through `EmailService` (from `User.Locale`, which the profile already stores) and through the public page routes in `FeedbackRoutes` (from the token's user, or `Accept-Language` for the page view).
3. `PublicPages` and `EmailActions.Label` taking a locale argument, and `lang` and `dir` set on the page and email HTML for Arabic.
4. The same verifier rules (completeness, placeholders, no em-dashes) as a test in `Test.Shared`.

Generated content (briefings, emails, and audio) is not UI chrome: it is written in each topic's `language` by the model.

## Message format

Messages are ICU MessageFormat:

- `{name}` is a placeholder. Keep the name exactly; move it wherever the target grammar needs it.
- `{count, plural, one {# item} other {# items}}` is a plural. Translate the text inside each branch and keep `#`, which prints the number. Each locale must spell out the plural categories its language uses for whole numbers: `one` and `other` for most European languages and Hindi; `one`, `few`, `many`, `other` for Russian; `zero`, `one`, `two`, `few`, `many`, `other` for Arabic; only `other` for Chinese, Japanese, and Malay. Exact matches such as `=0` or `=1` are allowed in any locale.
- `{kind, select, a {...} other {...}}` is a select. Keep the option keys exactly and translate the branch text.
- An ASCII apostrophe directly before `{` or `}` starts an ICU quoted literal and swallows the placeholder. Use the typographic apostrophe (’) for elisions such as French `d’{name}`.
- No em-dashes in any catalog. Rewrite the sentence instead.

## Adding a key

1. Add the English message to `dashboard/src/i18n/locales/en.json` under the right namespace (or to `mobile/src/i18n/catalog/en.js`).
2. Use it from the source with `t('namespace.key')`, or with a literal prefix such as `t('enums.runStatus.' + status)` for keys chosen at run time. The verifier treats a literal prefix as covering every key under it.
3. Add the translation to every other catalog, at the same path. The verifier fails until all 11 have it. When a translation is not available yet, have it machine-translated in the same change and note it for review; do not copy the English text.
4. Run `npm run i18n:verify` (dashboard) or `npm run i18n:check` (mobile).

Removing a key works the same way in reverse: remove it from every catalog, or the verifier reports it as orphaned in English and unknown in the others.

## Adding a locale

1. Add an entry to `SUPPORTED_LOCALES` in `dashboard/src/i18n/localeRegistry.js` and `mobile/src/i18n/locales.js` (code, English and native names, direction).
2. Add `dashboard/src/i18n/locales/<code>.json` and `mobile/src/i18n/catalog/<code>.js` (registering the latter in `catalog/index.js`), complete against English.
3. Update the locale list test in `dashboard/src/i18n/i18n.test.js`. No other code changes: the dashboard discovers the catalog by its file name.

## Verifiers

### Dashboard: `npm run i18n:verify`

`dashboard/scripts/verify-i18n.mjs` fails when:

- the source uses a key that `en.json` lacks, or `en.json` has a key nothing references (orphans);
- a supported locale has no catalog, a catalog misses an English key, or it has a key English lacks;
- any message fails to parse or format as ICU;
- a translation drops, renames, or adds a placeholder, changes an argument's type (plain, plural, select, number, date), or changes a select's options;
- a plural lacks `other` or a category its locale needs (`scripts/i18n-rules.mjs` derives these from `Intl.PluralRules` over whole numbers 0 to 1000);
- a translation drops a product name, URL, or route path that the English message contains;
- a catalog value contains an em-dash;
- JSX contains hard-coded user-visible text (text children, or `title`, `alt`, `placeholder`, `aria-label`, and similar attributes).

On success it prints the key count and the complete catalogs with their key counts.

### Mobile: `npm run i18n:check`

`mobile/src/__tests__/i18n.test.js` (part of `npm run verify`) checks the same things for the app: no missing or orphaned keys, a catalog for every locale, every English key translated in every catalog, valid ICU with the English arguments, the plural categories each language needs, and no em-dashes.

## Pseudo-locales and smoke tests

The pseudo-locales find problems that real translations would hide:

- **`qps-ploc` (expansion).** Every literal is accented, padded by about 40%, and bracketed: `Sign in` becomes `[Şīɠƞ īƞ~~~~]`. Truncated or overflowing text shows up as a missing bracket, and any plain English left on screen is a hard-coded string.
- **`qps-rtl` (right to left).** Every message is wrapped in right-to-left embedding marks and the document gets `dir="rtl"`, so layout mirroring can be checked without reading Arabic.

Placeholders and plural syntax pass through both transforms untouched.

`npm run i18n:smoke` runs `verify-i18n.mjs --pseudo` (which builds both pseudo-locales and formats every message in them) and then the Vitest suites under `src/i18n`:

- `pseudo.smoke.test.jsx` renders the login page, the shell, and the users page in the pseudo-locales and fails on surviving English text or unformatted placeholders.
- `rtl.smoke.test.jsx` renders the shell and navigation, the topics table with its row action menu, the profile form, and the Insights overview in `ar` and `qps-rtl`. Each must render with `dir="rtl"`, with every placeholder interpolated, and in Arabic without English navigation labels. The same file scans every stylesheet for physical `left` and `right` properties.
- `i18n.test.js` covers locale resolution, the formatters, the pseudo transforms, lazy catalog loading, and plural formatting in every locale.

## Right-to-left layout rules

- Use logical properties: `margin-inline-start`, `padding-inline-end`, `inset-inline-start`, `border-inline-start`, `text-align: start` or `end`. The stylesheet test rejects `margin-left`, `padding-right`, `left:`, `right:`, `float`, and `text-align: left` or `right`.
- Effects that only take physical values (an inset `box-shadow` used as an edge accent, a `translateX` slide-in) need a `[dir='rtl']` override beside them.
- Directional icons mirror under `[dir='rtl']` (`styles/components.css`): back and next arrows, disclosure and pagination chevrons, the sidebar panel toggles, sign in and sign out, send, and undo. Media, clock, refresh, and trend icons keep their orientation.
- Code, JSON, URL and email inputs, and monospace text stay left to right inside RTL pages, isolated so they do not reorder the surrounding text. The JSON tree keeps its chevrons unmirrored for the same reason.
- Charts are drawn in SVG coordinates that run left to right. Their SVG and the HTML axis labels under columns stay `direction: ltr` so labels line up with their bars; legends and card chrome follow the page direction.
- Positioned popovers (the row action menu) align to the trigger's inline-end edge: its right edge in LTR, its left edge in RTL.
